# Step 00: Project Setup

## Goal
Set up a clean, isolated Python environment and the project structure for a config-driven data pipeline, with the first data sources defined in YAML.

## Why

**Why a virtual environment (`.venv`)?**
Each project needs its own set of packages and versions. If everything is installed globally (or into Anaconda), projects can break each other when versions conflict. A virtual environment keeps this project's dependencies isolated and reproducible, so anyone who clones the repo can recreate the same setup.

**Why a hand-written `requirements.txt` instead of `pip freeze`?**
`pip freeze` dumps every installed package, sometimes with machine-specific paths that fail on other computers. Listing only the direct dependencies keeps the file short, readable, and portable.

**Why is `data/` in `.gitignore`?**
Data is an *output* of the pipeline, not source code. It can grow large, changes on every run, and can always be regenerated by running the pipeline. Git is for code and config, not data.

**Why is `sources.yaml` the heart of the project?**
This is a *config-driven* (metadata-driven) pipeline. The code is generic and the config decides *what* gets ingested. Adding a new data source means adding a few lines of YAML, with no new code. This is how real data platforms scale to hundreds of sources.

**Why this folder structure?**
| Folder / File | Purpose |
|---|---|
| `configs/` | Metadata: which sources to ingest and how |
| `ingestion/connectors/` | How to read each source type (API, CSV, database) |
| `ingestion/writer.py` | Writes raw data to the bronze layer as Parquet |
| `ingestion/state.py` | Tracks watermarks for incremental loads |
| `ingestion/runner.py` | Reads the config and runs every enabled source |
| `data/` | Local output (bronze / silver / gold), not committed |
| `docs/` | Step-by-step guide |
| `tests/` | Automated tests |

## Do it

**1. Clone the repo**
```powershell
git clone https://github.com/IqraBaluch/config-driven-data-pipeline.git
cd config-driven-data-pipeline
```

**2. Create and activate the virtual environment**
```powershell
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Mac / Linux
```

**3. Install dependencies**
```powershell
python -m pip install -r requirements.txt
```

## Check it works

1. The terminal line starts with `(.venv)`.
2. Python is coming from the virtual environment:
   ```powershell
   python -c "import sys; print(sys.executable)"
   ```
   The output should end with `.venv\Scripts\python.exe`.
3. The packages import without errors:
   ```powershell
   python -c "import requests, yaml, duckdb, pyarrow; print('All good!')"
   ```

## Common errors

**1. "Running scripts is disabled on this system" when activating**
Windows PowerShell blocks scripts by default. Fix (once per user):
```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

**2. pip says "Requirement already satisfied ... anaconda3"**
The virtual environment isn't active, so packages are going into Anaconda instead.
Fix: make sure `(.venv)` is shown, and use `python -m pip` instead of plain `pip`, so packages always go to the Python you are actually running.

**3. `requirements.txt` contains lines like `package @ file:///C:/b/...`**
It was generated with `pip freeze` from the wrong environment. Replace it with only the direct dependencies (see "Why" above).
